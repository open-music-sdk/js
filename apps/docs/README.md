# docs

The docs site, built with [VitePress](https://vitepress.dev/) and published to GitHub Pages from `main` at
[open-music-sdk.github.io/js](https://open-music-sdk.github.io/js/). Private: nothing here is published to npm.

## What's in it

```
.vitepress/config.mjs      the site: navigation, sidebars, search, and the base path /js/
.vitepress/frameworks.mjs  the frameworks a reader picks from, and how the choice is settled
.vitepress/variants.mjs    the ::: for blocks, and a search result for each of them
.vitepress/theme/          the default theme, with the framework picker added
index.md                   the home page
guides/                    how-to guides, one goal each
concepts/                  explanations: tokens, security, errors, packages, principles
samples.md, cli.md         the sample apps, and the command-line tool
glossary.md, differences.md, status.md
public/                    files served as they are, such as the logo
reference/                 generated by TypeDoc before each build, never committed
typedoc.config.mjs         the reference: every package, read from its source
typedoc.plugin.mjs         what the reference needs that TypeDoc does not do by itself
```

How to write a page, and which kind of page it is, is in [CONTRIBUTING.md](../../CONTRIBUTING.md#writing-docs).
A package's README opens its reference page, so the README is written for the site as well as for GitHub and npm.
It links to site pages by their full URL, `https://open-music-sdk.github.io/js/...`, which the site turns into a
relative link and checks like any other.

## Tasks

| Task | What it does |
| --- | --- |
| `pnpm --filter docs dev` | Writes the reference once, then serves the site. A page you edit reloads; a doc comment you change needs a restart. |
| `pnpm --filter docs build` | Writes the reference, builds the site to `dist`, and checks its anchors |
| `pnpm --filter docs check` | `typedoc --emit none`: the reference's checks alone, without writing anything |

CI runs `build` on every pull request that changes the docs or a package, and it fails on any of these:

- a comment that links to something that is not there, a name the reference refers to that is not exported, an
  export or namespace with no comment (TypeDoc's own validation);
- a function or method that leaves out an argument or what it returns, and a re-exported name that no package
  documents ([the plugin](./typedoc.plugin.mjs));
- a link to a page that is not there (VitePress);
- a link to an `#anchor` that names nothing on its page ([check-anchors.mjs](./check-anchors.mjs));
- a snippet of a sample app's file, `<<< @/../../samples/…#region`, whose file or region is gone
  ([check-snippets.mjs](./check-snippets.mjs)). VitePress would show the whole file instead, with no error. So
  is a snippet of a whole file that has regions, whose region lines the reader would see;
- a code block with a line over 80 characters, which the site would scroll (the same script);
- a group of framework variants that leaves out a framework, has two blocks for one, or has two blocks that show
  the same thing, and a heading inside a variant (the same script, as below).

A guide shows a sample's code with `<<<` rather than a copy of it, so that the code on the page is the code that
runs. A sample marks the lines a guide shows with `// #region <name>` and `// #endregion <name>`; rename one in
both places at once. The `#endregion` names its region, or VitePress doesn't end the region there. A file a page
shows whole, below its opening comment, is the region `file`, and the region lines inside it are left out.

## Code for each framework

The reader picks a client framework (Vanilla, React or Next.js) and a server framework (Express, Workers or Next.js)
in the nav, and each guide shows the code for those. Next.js on either side sets both, since a Next app is its own
server. The prose is the same for everyone; a block holds only what differs:

```md
::: for client=vanilla,react
The vanilla and React samples do it this way:

<<< @/../../samples/web-vanilla/src/errors.ts#explain{ts}
:::

::: for client=nextjs
The Next sample does it this way:

<<< @/../../samples/web-nextjs/src/lib/errors.ts#explain{ts}
:::
```

- Blocks next to each other, with only blank lines between, are one group, and the reader sees one block of it. A
  group covers every framework of its choice exactly once.
- What some frameworks share is one block for all of them, `client=vanilla,react`. What all of them share goes
  outside any block. Two blocks of a group that show the same thing, once their snippets are read in, fail the
  check.
- A block can name both choices, `client=react server=workers`. A group of those covers every client and server the
  samples run together: either Vite page with either server, and the Next app alone.
- A block that holds a container of its own, such as a code group, opens with four colons, `:::: for client=react`,
  and closes with four, so that the inner `:::` doesn't close it. A line of colons alone closes a block even inside
  a code block, and the check fails either mistake.
- A heading goes above the blocks, never in one. A block's id is the heading's, then its frameworks, such as
  `#_2-act-on-each-kind--nextjs`, and the search lists each block as a result of its own under that heading. A link to
  that id switches the reader to those frameworks. In the search's detailed view such a result shows no excerpt:
  VitePress cuts excerpts at headings, keyed by the heading's id, and the block's id is no heading's.
- A link can also carry a choice, `?client=react&server=workers`.
- A page for some frameworks alone says so in its frontmatter, `for: client=react,nextjs`. The sidebar and the
  pager leave it out for a reader who chose others, the page tells such a reader so, with a button that switches,
  and the check holds its groups to those frameworks alone.

Getting started's two pages set up each server and client in blocks, as the guides do. What only one framework
does, such as caching on a Next server or deploying a Worker, is a guide with `for:`.

The plugin also:

- shows a function built by one of core's builders with its arguments one by one, instead of as one rest tuple,
  and with the comment written on it rather than the one on core's call signature;
- documents each name once, in the package that declares it. `server`, `browser` and `react` re-export most of the
  family, and without this every type would have a page under each of them;
- reads functions and methods only. A member of a namespace interface, such as `music.catalog.getSong`, is a
  property, and each client's tests hold its tags to its function's instead.

Packages are read from their source through TypeScript `paths`, so a link from one package to another resolves
and the reference needs no build first.

## What every function says

Every exported function, every method of a class, and every method of an interface an app calls or implements says
three things, and so does each member of a namespace such as `music.catalog`:

- what each argument is, with a `@param` for each;
- what it returns, with `@returns`, unless it returns nothing;
- what it throws, with a `@throws` for each kind of error: a `TypeError` for a caller's mistake, an
  `AppleMusicError` for what happens at runtime. A rejection counts as a throw.

**A function with no `@throws` throws nothing.** The absence is a statement, so every function that can throw names
each error it can. No check can tell a function that throws nothing from one whose `@throws` was forgotten, so that
is read for in review.

A function declared as a const built by a call, as the clients' endpoint functions are, carries `@function` so that
TypeDoc shows it as one.
